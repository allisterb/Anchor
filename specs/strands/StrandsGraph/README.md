# StrandsGraph

**The Strands graph executor as it actually runs**, rather than the orchestrator a paper would
specify. Where [`DependencyDAG`](../DependencyDAG) asks *does the paper's Host Agent behave?*, this
asks *what will my workflow actually do when Strands runs it?*

| file | what it is |
|---|---|
| `StrandsGraph.tla` | the executor loop and four properties. Verifies on the guarded workflow. |
| `StrandsGraph.cfg` | |
| `Workflow.tla` | the graph, shared in form with `DependencyDAG` — swappable, and generated by `graph_to_tla.py`. |

New to TLA+? [`specs/DependencyDAG/README.md`](../DependencyDAG/README.md) has a notation primer and
the full account of how a Strands graph is translated.

```bash
python tests/strands/graph_to_tla.py
```

## Why this is a separate model

`DependencyDAG.tla` cancels an orphaned subgraph and requires every task to reach a terminal state.
**Strands does neither.** It has no `CANCELED` status, it fail-fasts the whole run when a node
raises, and when nothing is ready it simply *stops* — leaving whatever was never admitted unrun, and
reporting success. Modelling both orchestrators in one file would mean checking properties of a
system nobody is running.

The loop, from `Graph._execute_graph`:

```python
while ready_nodes:
    current_batch = ready_nodes.copy()
    ready_nodes.clear()
    await self._execute_nodes_parallel(current_batch, ...)
    newly_ready = self._find_newly_ready_nodes(current_batch)
    ready_nodes.extend(newly_ready)
```

Three details do all the work:

1. **The batch is awaited as a whole.** `_execute_nodes_parallel` does not return until every node
   in it has finished, so nodes that share a batch always complete together.
2. **Readiness is recomputed per completed batch**, and only from edges out of *that* batch. An edge
   that fired earlier does not disqualify a later one.
3. **The loop has no exit check.** It ends when `ready_nodes` empties, and nothing asks whether
   anything was left out.

## The state

```tla
VARIABLES
    status,     \* [Tasks -> {"UNRUN", "RUNNING", "COMPLETED", "FAILED"}]
    runs,       \* [Tasks -> Nat] -- how many times each task has been admitted
    ready,      \* queued for the next batch
    batch,      \* executing right now
    phase,      \* "RUNNING" | "DONE" | "ABORTED"
    oracle      \* undeclared edge conditions, as in DependencyDAG
```

`Status` is the **SDK's** vocabulary, not the paper's — there is no `CANCELED`, because Strands has
none. `UNRUN` covers both "not reached yet" and "never will be": the executor does not distinguish
them, and neither does this model.

`Workflow.tla` is shared with `DependencyDAG` unchanged. That works because a condition can only
observe the two statuses Strands writes into `state.results` — `COMPLETED` and `FAILED` — and both
models spell those the same.

## The properties

| | |
|---|---|
| `NoSilentSkip` | the run reported success and something never ran. **The one this model exists for.** |
| `HP10` | a task runs only once every parent has completed. Restated here so one workflow can be checked against both models. |
| `RunsAtMostOnce` | no task is admitted twice. An agent admitted twice is invoked twice — charged twice, and its output recomputed. |
| `Terminates` | the loop always leaves. Deliberately weaker than `DependencyDAG`'s `AllTerminate`: it says the **run** ends, not that the tasks did. |

Each isolates cleanly to the graph shape that causes it. **Checked one invariant at a time**, and
that matters: TLC stops at the first violation, so the combined `.cfg` cannot attribute a failure —
on the skew graph `RunsAtMostOnce` is masked by `HP10`. `graph_to_tla.py` rewrites the config per
property and reproduces this table on every run, so it is computed rather than transcribed:

| | unguarded diamond | skew | router |
|---|---|---|---|
| `NoSilentSkip` | ok | ok | **VIOLATED** |
| `HP10` | ok | **VIOLATED** | ok |
| `RunsAtMostOnce` | ok | **VIOLATED** | ok |

and every one matches a probed SDK behaviour:

```
docs diamond  ['research', 'analysis', 'factcheck', 'report']   report ran 1x
skew          ['A', 'B', 'C', 'C']                              C ran 2x
router        status=COMPLETED, ran ['plan', 'reject'], 2/3 nodes, skipped ['approve']
```

## `NoSilentSkip`, and why it needed its own model

```tla
NoSilentSkip == phase = "DONE" => \A t \in Tasks : status[t] # "UNRUN"
```

A node whose incoming conditions never pass is never run, never appears in `results`, and the graph
reports `Status.COMPLETED`. No hang, no error, no warning. **A workflow can silently drop part of
its graph and still look successful** — and on a two-branch router, "part of its graph" is a third
of it.

`DependencyDAG` cannot state this. Its orchestrator *cancels* what it cannot admit, so every task
reaches a terminal state and the property is satisfied honestly. The failure class does not exist in
that machine.

## Where the two models disagree

`graph_to_tla.py` runs one graph against both, with the SDK's own behaviour beside them:

```
  graph                      DependencyDAG   StrandsGraph   the SDK
  docs diamond, unguarded    VIOLATED        HOLD           report ran 1x, after both parents (3/3)
  docs diamond, guarded      HOLD            HOLD           report ran 1x
  skew, unguarded            VIOLATED        VIOLATED       C ran 2x
  skew, guarded              HOLD            HOLD           C ran 1x
  router, opaque conditions  HOLD            VIOLATED       COMPLETED having run 2/3 nodes
```

Two disagreements, in **opposite directions**, and neither model is simply wrong.

**The diamond.** `DependencyDAG` says VIOLATED; the executor cannot do it. Both parents are seeded
into one batch and awaited together, so `report` always sees both. `DependencyDAG` has no batches
and interleaves tasks individually, so it **over-approximates**: *holds* there means holds in
reality, but *VIOLATED* may be spurious — as it is here. That is the ordinary price of an
abstraction, but it has to be stated, because a spurious counterexample looks exactly like a real
one.

**The router.** `DependencyDAG` says HOLD; the executor drops a node. That is not imprecision, it is
a **different machine**. Its orchestrator cancels what it cannot admit, so the property is satisfied
honestly.

Which is the argument for keeping both, rather than picking one.

## What this model does not cover

- **What a task does.** Agents appear only as completing or failing. Nothing here says their outputs
  are correct.
- **Interrupts and `reset_on_revisit`.** The executor supports both; neither is modelled, and
  re-execution is counted (`runs`) rather than given semantics.
- **Timeouts.** `node_timeout` and `execution_timeout` turn into failures in the SDK; here failure is
  simply nondeterministic, which covers them without naming them.
- **Time-varying conditions.** `oracle` is fixed per behaviour, as in `DependencyDAG` — see that
  README for why, and for what it costs.
